# Codegenie Pulse Connector 1.2.1

## Summary

Codegenie Pulse Connector 1.2.1 is a maintenance release that clarifies privacy and external-service disclosures, adds a WordPress Privacy API suggestion, and makes one-time provisioning and multisite activation more fault tolerant. The connector protocol and capture categories are unchanged.

## Changes

- Corrected consent text so it describes the actual connection payload and does not claim that an installed-plugin inventory is sent.
- Added a translatable privacy policy suggestion through `wp_add_privacy_policy_content()` in the WordPress administration context.
- Documented the official Codegenie Pulse terms and privacy pages and the policy responsibility of alternative compatible Pulse installations.
- Detects failed or partial option writes during the one-time exchange and preserves the previous configuration on failure.
- Rejects exchange responses whose configuration is bound to a different Pulse origin.
- Uses local token-safe exchange messages and applies bounded backoff to every rejected 4xx ingestion response.
- Installs non-autoloaded defaults for every site during multisite network activation.
- Expanded privacy, fault-tolerance, redaction, backoff, handler, migration and multisite regression coverage.

## Compatibility

- WordPress 6.2 or newer.
- Tested with WordPress 6.2.0 and 7.0.2.
- PHP 7.4 or newer; tested with PHP 7.4.33, 8.3.14 and 8.5.1.
- Requires PHP OpenSSL support for AES-256-GCM.
- Plugin directory, installation slug and text domain: `codegenie-pulse-connector`.
- Connector ID: `codegenie-pulse-connector-wordpress`; protocol version 1.

## Upgrade behaviour

There is no database-schema migration. Existing 1.2.0 option names and values are retained, including the encrypted DSN, capture mode and verification token. If WordPress authentication salts changed, the existing DSN cannot be decrypted and must be entered again. A failed automatic exchange returns an error instead of reporting a partially persisted connection as successful.

## Privacy and data transfer

After explicit administrator approval, the connection exchange can send the site URL, site name, WordPress version, connector version, PHP version, environment type, multisite status and one-time technical authorization data to the selected Pulse installation. It does not send an inventory of installed plugins or plugin versions.

Error events can contain bounded, redacted technical error fields. Deployment tracking can send the change type, component slug and version. Cookies, authorization headers, incoming form data and request bodies, email recipients or content, and WordPress users are not sent. Retention and data-subject rights follow the terms and privacy notice of the selected Pulse installation.

## Security-relevant changes

- Failed or filtered option writes no longer leave the exchange appearing successful.
- A Pulse response cannot switch the accepted connection to another origin, and remote response text is not rendered as an administrator notice.
- Sensitive endpoint credentials remain encrypted with AES-256-GCM and are not rendered in diagnostics.
- Outbound ingest and exchange requests continue to use `wp_safe_remote_post()`, zero redirects and bounded timeouts.
- Existing redaction, recursion protection, backoff, capability and nonce controls remain enforced.

No exploit details or production credentials are included in this release material.

## Known limitations

- The plugin has no queue and does not retry dropped events; it uses local backoff to avoid event storms.
- Salt changes require the DSN to be entered again.
- Existing `debug.log` and PHP `error_log` files are not imported.
- An administrator using another compatible Pulse origin must review that installation's terms and privacy notice.
- WordPress.org icons, banners and screenshots still require approved Codegenie brand assets and synthetic screenshots.
- The tracked WordPress.org asset manifest records these missing human deliverables explicitly; it does not approve or generate them.

## Rollback and support

For rollback, deactivate 1.2.1 and reinstall the reviewed 1.2.0 package without uninstalling first. Uninstall deliberately removes settings and secrets, including across multisite, and is therefore not a rollback mechanism. A published WordPress.org tag is immutable; any post-publication fix receives a new patch version.

Use the repository's normal support channel for non-sensitive issues. Report vulnerabilities through GitHub private vulnerability reporting as described in `SECURITY.md`; never post DSNs, tokens, personal data or private logs publicly.
